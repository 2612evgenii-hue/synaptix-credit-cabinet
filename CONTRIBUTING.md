# Работа с кодом SYNAPTIX

## Один поток интеграции

`main` — проверенное состояние. Постоянная ветка `develop` для команды из трёх
человек не нужна. Одна задача — одна короткая ветка — один PR. Интегрировать
работу ежедневно; незавершённые функции скрывать настройкой, не ломать основной путь.

```sh
git switch main
git pull --ff-only
git switch -c feat/12-application-draft
# изменить файлы, проверить
git add <конкретные-файлы>
git diff --cached
git commit -m "feat(application): save application draft"
git push -u origin HEAD
gh pr create --draft
```

Ветки: `feat/12-topic`, `fix/12-topic`, `docs/12-topic`, `chore/12-topic`,
`test/12-topic`, `refactor/12-topic`, `hotfix/12-topic`; служебные ветки агента —
`codex/topic`. Номер — реальный Issue; не создавайте фиктивные связи.
Имена краткие, латиница, цифры и дефисы.
Для Dependabot допускаются его ветки `dependabot/github_actions/...`;
заголовки PR и коммитов остаются Conventional Commits (`ci(deps): ...`).

## Коммиты

Conventional Commits: `type(scope): смысл изменения`.
Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `revert`.
Scope необязателен. Заголовок не длиннее 100 символов. Описание допускает русский.
Для несовместимого контракта: `feat(api)!: ...` и `BREAKING CHANGE:` в теле.
Один коммит — одна понятная работа. Не использовать `update`, `final`, `fix all`.

У каждого собственные GitHub-аккаунт, email и ключ. Не подменять автора и даты.
Совместная работа: `Co-authored-by: Name <согласованный-email>` с согласия соавтора.
Коммиты агента проверяет человек; используйте `Assisted-by: Codex` в теле.
Не выдумывать промежуточные коммиты ради количества.

`bootstrap.py` подключает versioned hooks только в этом клоне. Hook можно обойти;
он дополняет серверные проверки. CI проверяет заголовок PR и каждый коммит в PR.

## Pull Request

Указать `Closes #<issue>`, результат, способ проверки, риски, миграции и откат.
Перед Ready for review обновить ветку относительно `main`; для общей ветки
использовать merge `origin/main`. Переписывать опубликованную общую ветку нельзя.
Своя ветка: rebase возможен только по согласованию; push только `--force-with-lease`.
В `main` force push запрещён.

Один независимый approve обязателен. Новые коммиты сбрасывают approve.
Автор и автор последнего push не принимают собственное изменение. Все обсуждения
закрыты; обязательные `repository-policy` и `secret-scan` зелёные, ветка актуальна.
Все три участника указаны владельцами кода: у автора остаются два возможных ревьюера.
Главный администратор управляет доступом и настройками. Аварийный обход правил
допустим только как явное действие администратора с записью причины и последующим ревью.
Действие правил зависит от фактической поддержки GitHub — см. `docs/github-status.md`.

Merge-метод — **squash**: заголовок PR становится заголовком коммита в `main`.
Исходные коммиты сохраняются в PR, итог и авторство — в Git. PR body содержит ссылки
на соавторов и Issue; при squash проверять trailers. Ветка после merge удаляется.

## Версии и журнал

До первой рабочей версии — `[Unreleased]` в CHANGELOG. Затем SemVer:
`v0.1.0` — первый сквозной MVP, `v0.1.1` — совместимое исправление,
`v0.2.0` — новые возможности. Тег сдачи, например `v1.0.0-hackathon.1`,
выбирается один раз и не перемещается. Не создавать тег релиза на неготовом каркасе.

Изменение поведения обновляет CHANGELOG, API — OpenAPI и коллекцию,
архитектуры — ADR, зависимости — lock-файл и THIRD_PARTY_NOTICES.
В `docs/action-log.md` писать значимые решения, изменения доступа и инциденты.
Обычные правки автоматически доступны через Git/PR и `make audit`.

## Откат и конфликты

Конфликт согласовать с автором области, просмотреть diff, повторить затронутые
проверки. Чужие изменения не удалять ради разрешения конфликта.
Откат: новый PR с `git revert <sha>` и заголовком коммита `revert: ...`;
не `reset --hard` и не force push в `main`.
Изменение схемы БД требует плана обратимости или восстановления из резервной копии.
Перед тегом сдачи сделать `make backup`; хранить bundle вне рабочего компьютера.

## Definition of Done

- Задача и критерии приёмки выполнены; есть проверка результата.
- Нет секретов, реальных банковских или персональных данных.
- Контракты, документация, CHANGELOG и notices актуальны.
- CI проходит, независимое ревью получено, обсуждения закрыты.
- Основной сценарий остаётся воспроизводимым; изменения готовы для демонстрации.
