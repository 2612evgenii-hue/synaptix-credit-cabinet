# Безопасность SYNAPTIX

Главный администратор — `2612evgenii-hue`. Каждый использует личный аккаунт,
2FA, отдельный ключ/токен с минимальными правами. Общих аккаунтов и токенов нет.
В личном репозитории владелец имеет admin, приглашённые участники — write;
требовать 2FA централизованно здесь нельзя. Для управляемых командных ролей,
read-only-доступа жюри и организационного аудита предпочтительна GitHub Organization.
Создание организации и платная подписка не выполняются автоматически.

## Данные и секреты

В Git — только синтетические данные. Нельзя добавлять реальные заявки,
паспортные данные, финансовые документы, production-dump и ключи.
`.env` игнорируется; `.env.example` описывает переменные без рабочих значений.
Секреты CI хранятся в GitHub Secrets, рабочий прототип должен запускаться без
платных API и корпоративных сервисов. Базовый CI не получает секретов приложения.
Gitleaks сканирует всю доступную Git-историю с `--redact`; это поиск известных
паттернов, а не доказательство отсутствия утечек и не DLP.

## Репозиторий и CI

Целевой профиль: обязательный PR и одно независимое ревью, защита администраторов,
актуальная ветка, сброс старых approve, запрет force push/удаления `main`,
закрытые обсуждения, только squash. Релизные `v*` защищены от изменения и удаления.
Профили в `config/github/` — желаемые настройки; реальное применение проверяется
через `scripts/github_audit.py` и записывается в `docs/github-status.md`.

CI использует `pull_request`, не `pull_request_target`, `contents: read`,
`persist-credentials: false`, ограничения времени. Actions закреплены полным SHA.
Скрипты и workflow из PR тоже могут меняться: их обязательно просматривает коллега.
Изменения `.github/`, `scripts/` и профилей безопасности требуют особого внимания.
Dependabot обновляет Actions; для будущего стека добавить его package ecosystem.
Нет автоматической публикации, merge или развёртывания из PR.

## Утечка или компрометация

1. Сразу отозвать/заменить секрет у поставщика. Удаление файла не отзывает ключ.
2. Сообщить главному администратору закрытым каналом; не публиковать секрет в Issue.
3. Ограничить доступ затронутого аккаунта, проверить Actions и изменения настроек.
4. Записать время, затронутую область и меры в закрытом журнале без значения секрета.
5. Очистку истории согласовать отдельно: она меняет SHA, копии и ссылки на сдачу.
6. Восстановить доступ после проверки, повторить аудит и сканирование истории.

Git и локальный Markdown-журнал изменяемы администратором и не дают неизменяемого
полного аудита. Экспорт Git не включает настройки аккаунтов, локальные несохранённые
действия, чаты и все события GitHub. GitHub Organization audit log, ограничения хранения
и внешний архив рассматриваются отдельно при необходимости.
