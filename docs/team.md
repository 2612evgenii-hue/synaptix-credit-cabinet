делаются после согласования, чтобы не выдавать предложение за обязательство.
При уходе одного участника второй может проверить изменения третьего.

## Onboarding

1. Принять приглашение с правом write; проверить возможность PR. Репозиторий public.
2. Включить 2FA и сохранить recovery codes отдельно от Git.
3. Проверить `git config user.name` и `git config user.email`; не использовать
   чужой адрес. GitHub noreply допустим.
4. Запустить `python3 scripts/bootstrap.py`, `make check`, установить Gitleaks.
5. Создать небольшую рабочую ветку; пройти PR и независимое ревью.
6. Проверить, что прямой push в `main` реально блокируется сервером после
   активации защиты; локальные hooks не являются доказательством.

## Рабочий ритм

Issue → In progress → PR draft → Review → Done. Это простой процесс в Issues/PR;
GitHub Project автоматически не создаётся. Ежедневно сверять цель демонстрации,
открытые блокеры и интеграцию. Приоритет P0 — сквозной сценарий и условия сдачи.
P1 — обработка ошибок и качество; P2 — улучшения после рабочего MVP.

Не держать общий файл одновременно без координации. Перед изменением контракта
согласовать OpenAPI; каждый следующий PR проверяет совместимость с ним.
